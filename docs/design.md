# Claude Cache Keeper

## Purpose

Keep the prompt cache of selected, running Claude Code GUI conversations warm without adding maintenance messages to their transcripts. Target Claude Code 2.1.300 and VS Code's native Claude chat. Codex is out of scope. The user approved the native in-session approach in the preceding research and requested implementation.

## Design

A Claude Code mod runs independently in each loaded conversation. `/cache-keeper` opens a native pane containing a session-local on/off button, a TTL toggle, estimated remaining cache lifetime, consecutive refresh count, and the last measured read/write token counts. A dedicated pane avoids competing with the user's existing cozy-clawd band. Text arguments provide the same controls if panes are unavailable. No separate VS Code extension or external CLI resume process is required.

Start disabled. A user can enable the current session. Track the main conversation's actual model request times and successful completion. A refresh is eligible only after a successful main request, while idle, before its cache expires, and within the idle and refresh limits. The default TTL is explicitly one hour and the lead is five minutes; support an explicit five-minute setting with a one-minute lead. Set the main-request TTL while streaming a real request when enabled. Match the fork TTL for the duration of the request and restore the previous process environment in `finally`. Respect a pre-existing forced five-minute TTL; if it changes between the main turn and a fork, refuse the fork instead of silently changing the user's configuration. Do not change persistent TTL settings.

Use `$.model.fork` with a request for one period. Preserve the main request's model, prompt, tools, and effort. Do not submit a real conversation turn, spawn a shell, call tools, or read conversation files. A warm response is accepted only when it contains valid usage and at least 95% of its input is cached, with at most 1024 uncached input tokens. On an API failure or poor hit, stop refreshing until a subsequent successful real turn. A successful ping is evidence of a cache read, not proof of the lifetime of a later request; label the timer as an estimate.

At most three refreshes and three hours of human inactivity by default. Do not refresh a cache that already expired (including after sleep), and never overlap refreshes. Main-turn activity wins any race with a refresh: stale refresh results cannot reset counters or timestamps for the new turn. Turning off invalidates an in-flight result, although an already sent request may still be charged. A stopped session may be enabled again after a new successful real turn. State is local to the running session and starts disabled after a reload.

## Deliverables and checks

Standalone source project `claude-cache-keeper`, local marketplace metadata, installation instructions, and an install script or direct local marketplace installation. Use exact declarations generated by Claude Code 2.1.300 where available. Validate the plugin with the installed CLI, type-check it, and use Claude's native mocked-clock tests for the GUI buttons, refresh timing, races, TTL restoration, hit validation, and session isolation. No paid model call is needed for these tests.

Install the validated local plugin for the user, initially disabled for each conversation. Do not overwrite existing Claude settings. Existing sessions require plugin reload or reopening. The installed VS Code extension must also be 2.1.299 or newer; updating only the standalone CLI is insufficient for the band.

A real cache-lifetime experiment remains distinct from mocked tests: use a disposable GUI conversation with sufficient cacheable context, compare cold and refreshed runs across the original expiry, and inspect the next real turn's cache reads. Report whether that experiment actually ran.
