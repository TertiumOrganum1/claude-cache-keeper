# Как работает прогрев

## Строка над полем ввода

Слева направо: занятый контекст, процент чтения из кэша в последнем запросе, лимиты подписки 5h и 7d (до получения данных - `?`), модель и effort, переключатель `Кэш: вкл/выкл`, время до следующего прогрева и число успешных прогревов, кнопка `Прогреть`. Строка не переносится; в узкой панели доступна горизонтальная прокрутка. Отдельных окон и всплывающих уведомлений нет: ошибки и промахи показываются в самой строке.

## Прогрев

Прогрев - вызов `model.fork` с просьбой ответить одним символом поверх контекста чата. Модель, system prompt, инструменты и effort берутся из последнего обычного запроса, поэтому префикс совпадает и читается из кэша. В ленту чата прогрев не попадает, инструменты не вызываются.

Пример из реального чата с контекстом около 190 тыс. токенов:

| Прогрев | Вход | Выход | Чтение из кэша | Запись в кэш |
|---|---|---|---|---|
| первый после ответа Claude | 14 | 3 | 190 949 | 3 045 |
| следующий, через 55 минут | 14 | 3 | 193 994 | 0 |

Первый прогрев после обычного ответа один раз дописывает в кэш сам этот ответ, его там ещё не было. Следующие прогревы ничего не пишут.

## Когда отправляется

- Основные запросы и прогревы используют одинаковый явный TTL `1h`, если настройки Claude его разрешают. Режим `5m` включается командой `/cache-keeper on 5m`.
- Плагин проверяет срок каждые 15 секунд и отправляет прогрев за 5 минут до истечения (в режиме `5m` - за минуту).
- Прогрев включён по умолчанию, но нужен успешный обычный запрос в этом чате. В пустом чате и после перезапуска VS Code до нового ответа Claude API возвращает `nothing-to-fork`: запрос к модели не отправляется, строка объясняет, что нужен ответ Claude. Старая история сама по себе не подходит.
- Уже истёкший кэш автоматически не пересоздаётся. Закрытый VS Code, спящий компьютер или остановленный процесс таймеры не выполняют.
- Ограничения по числу прогревов нет: пока чат открыт и прогрев включён, он идёт примерно раз в 55 минут.

## Проверка результата

Прогрев засчитывается, только если usage подтверждает чтение из кэша: не меньше 1024 токенов cache read и не меньше 95% входа последнего обычного запроса. Ответ и результаты инструментов после этого запроса могут добавить сколько угодно новых токенов, на проверку это не влияет. Если вход обычного запроса ещё неизвестен, берётся доля чтения не меньше 95% от входа самого прогрева.

Промах или ошибка не превращаются в фиктивный успех: таймер не продлевается, причина видна в строке, автоматика ждёт следующего обычного ответа или нажатия `Прогреть`.

## Защита от гонок

- Смена модели, effort, набора инструментов, `/clear`, `/compact`, `/resume` и подобные команды сбрасывают отсчёт.
- Прогрев не пересекается с другим прогревом и с обычным запросом. Запоздавший ответ прогрева не перезаписывает состояние нового хода.
- Временные переменные окружения TTL восстанавливаются после запроса. Заранее заданный принудительный TTL `5m` уважается: если он изменился между обычным запросом и прогревом, прогрев не отправляется.
- Состояние чата хранится в session state Claude Code и переживает перезагрузку кода плагина. Каждый чат независим.

## Команды

- `/cache-keeper`, `/cache-status` - подробное состояние: причина, время следующего запроса, TTL, число прогревов, оценка остатка кэша, счётчики usage, последняя ошибка.
- `/cache-on`, `/cache-off`, `/cache-keeper on|off` - прогрев в текущем чате.
- `/cache-keeper now` - прогреть сейчас; повторный вызов не отменяет запрос, который уже идёт.
- `/cache-keeper on 1h`, `/cache-keeper on 5m` - TTL последующих запросов.
- `/cache-keeper clock on|off` - правка штатного таймера, см. [native-clock.md](native-clock.md).

Таймер в строке - оценка по времени начала запроса, а не остаток, полученный от сервера.
